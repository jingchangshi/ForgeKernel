# 决策叙事：Agent 每次在想什么、凭什么、为什么错

**作者**：lead。**日期**：2026-11-03。
**性质**：解释性的，不是流水账。逐轮数字在 `raw-forgekernel-iterations.md`；取证在 `evidence/intervention-timeline.md`。

---

## 0. 一句话

这条轨迹不是「调参一路变快」，而是**四次把「瓶颈在哪」判断错，又四次被证据打脸**。真正抬高性能的只有 6 条改动；把 prefill 从 0.39× 抬过 1.0 的那两下，都不在 kernel 里。

---

## 1. Era A：为什么一开始走 SIMT 就注定慢

**起始信念**：`rmsnorm_cw4/kernel.py` 用 `T.SimtVF(threads=)`，把 Ascend 向量单元当成**SIMT 线程组**模拟。这条路径能编译、能跑、decode 还能赢厂商一点（1.095×），所以**它不显得错**——这是最危险的一类错：有真实的正收益掩护。

**信念错在哪**：Ascend 的向量单元是 **SIMD**（一条指令作用一整条向量寄存器），不是 SIMT 的「多线程各算一个元素」。用 SIMT 模拟 SIMD，等于用 256 个线程去拼一条向量指令，向量效率天然差 3×。

**这一层为什么当时看不见**：官方 TileLang RMSNorm 示例 `examples/ascend/example_rmsnorm.py` **用的就是同样的 SimtVF 结构**。agent 专门查过（seq 12410）：「官方示例本身就是这个 SIMT 路径」。也就是说，**照抄官方示例＝照抄了一条次优路径**，而官方示例的存在恰恰让人相信这条路是对的。

### 1.1 转向是怎么发生的（归因要说准）

10 个实验（E1–E10）之后，prefill 卡在 **0.388×**，agent 自认「structural wall」（seq 12242 原文）。在 round 8 收尾的**同一段推理末尾**，agent 自己写道「Actually — SimtVF vs SimdVF: there's also SimdVF」，并立刻查了 SimdVF API（seq 12243，10:37:28）。

几乎同时，操作者发来了那次关键纠正（原话见 `evidence/intervention-timeline.md`）：「使用了 SIMTVF，而 rmsnorm 类算子理论上使用 SIMDVF+DMA 访存才能达成极致性能。按照这个思路，使用 agent team 审视接下来的性能优化工作。」

**准确的归因**：不能说「agent 完全没想到、全靠操作者点破」——证据显示 agent 在同一小时内已经摸到门口；也不能说成「agent 自己发现的」——操作者的消息把它**指令化**，并加了「用 agent team」这个组织要求，这确实改变了后续形态。**两者几乎同时到达，操作者的消息是那个把念头变成方向的节点。**

**结果**：SimdVF 单行 `max_abs=0.0`（优于 SimtVF 的 0.015625），多核 prefill 到 0.62×，同窗口 ABBA 显示 SimdVF 比 SimtVF 快 ~1.208×。**换范式是对的，但只到 0.62×，还不够。**

## 2. Era B：从「结构调参」到「L2」，以及一次自我推翻

**第二信念**：「慢了就是流水线/结构没调好」。于是 rows、stages、多累加链、双缓冲轮番上。**这个信念把 prefill 从 0.62× 推到 ~0.75×，然后彻底停住。**

**关键转折不是一次成功，是一次否定被推翻**：R64 量了拷贝路径 ~1.7 TB/s，算出 128 MB 纯拷贝要 0.078 ms，于是**宣告 copy 路径触底**——意思是不用再在访存上想。**R65 立刻打脸**：显式给写路径 `NORMAL_FV`，写带宽从 1.13 跳到 **3.08 TB/s（2.7×）**。

> **这里最值得记的一课**：R64 的推理链本身没错（拷贝确实那么慢），错在**它默认「当前的 cache 策略」是给定的**。一个「触底」判断如果没问「这个底是物理的还是配置的」，就会把配置问题误判成物理极限。**Era B 后半段的 8 个否定（R68-70）之所以没找到东西，前提也建立在这个被推翻的「底」上。**

**另一课（R66）**：微基准里 `NORMAL_LV` 读策略第一，进真实内核反而更慢。**孤立基准的第一名，进混合流量就作废。** R73 印证：读写各自很快（2.35 / 3.08 TB/s），混合只 1.76——**gap 在混合效率，不在单条路径。**

**R80 的收尾是诚实的**：decode 三窗 EXCEED，prefill 四窗 FAIL（0.771–0.850），`objective_met=false`，明确写「杠杆耗尽」。**它是对的——在当时的信息下，能想到的杠杆确实试遍了。**

## 3. Era C：为什么参考资料能撬开一个 80 轮没撬开的门

这是整个练习里**最可迁移的一段**，值得慢慢说。

R80 之后 agent 先试了一条更「聪明」的路：**msprof op 模拟器**，想在离线仿真里找答案。R81 能跑，R82 澄清了命名，**R83 把它自己判死**——v23 和 v28 在仿真里 **bit-identical**（都是 338639 cycles），可它们在真机上差 12%。**一个分不出 12% 的 oracle 不是 oracle。** 这条路的关闭是对的，而且是被自己的证据关掉的。

然后操作者给了参考资料（seq 20119）：AscendC 的**手写算子**教程仓库，特别指向 `02_reg_compute/softmax_high_performance`。

**为什么这能撬开？** 不是因为它给了答案，而是因为它**换了提问的方式**。前 80 轮 agent 一直在问「我的 TileLang kernel 里还能调什么」——这是一个**在给定的 kernel 结构内部搜索**的问题。读厂商手写实现之后，问题变成「**厂商在同样的硬件上，是靠什么结构拿到那个带宽的**」——这是一个**跳出当前结构**的问题。

后者才问得出这两件事：

1. **启动几何**：芯片只有 **56** 个 AIV 核（三处独立声明 + step-detection 探针证实 grid 1..56 平坦、57 跳 +82%），而 kernel 一直按 **64** 块启动——**多出的 8 块要跑一个几乎空的第二波**。这是纯 host 侧的一行改动。
2. **读路径 cache 策略**：X tile **只读一次**，不该占用 L2 名额去挤掉被反复读的操作数。`NOTALLOC_CLEAN` 正是「流式一次、不进 L2」——而它给出的收益是 **1.103×**。

**这两个都不在 kernel 体里。** 调了 80 轮的 kernel 体，最后跨过 1.0 的 15%，在 kernel 外面。

### 3.1 但要诚实：参考资料是「提示」，不是「答案」

细节见 `reference-materials-role.md`。要点：**56 这个数字不是 devkit 写的**，是 agent 自己的 step-detection 探针测出来的——devkit 提示了「去看厂商怎么组织」，探针给了数字。**把功劳全记在 devkit 上，会把教训记错**：真正的教训是「换一个层次的提问」，不是「某一篇文档里有答案」。

## 4. 四次判断错误，列表如下（这是本报告的主结论）

| # | 当时的判断 | 真相 | 谁纠正的 |
|---|---|---|---|
| 1 | SIMT 模拟够用（官方示例就这样） | 向量单元是 SIMD，SIMT 天然慢 3× | agent 与操作者几乎同时 + 操作者指令化 |
| 2 | copy 路径已触底（1.7 TB/s） | 「底」是 cache 配置造成的，不是物理 | R65 的 2.7× 写带宽 |
| 3 | 微基准第一进内核也第一 | 混合流量下排序翻转 | R66 |
| 4 | 离线模拟器能找到答案 | 分不出 12% 差异 | R83（自我否定） |

**这四条的共同形状**：判断都建立在「把某个当前配置当成物理约束」上。**这不是粗心，是搜索的固有盲区**——你在一个结构里找，就看不见结构的边界。参考资料的作用，是强制你换一个结构看。

## 5. 本会话的 v34：一个小而干净的收尾

操作者指出 `T.simd.vcadd` 是全归约、不是对折。**他说对了**（实测：ones→64.0 于 lane0、单非零车道；ramp→2016=sum(0..63)）。但**内核没算错**——因为 `vcadd` 用 `MODE_ZEROING`，链是**幂等**的，6 次调用 = 1 次的结果。坍缩后 **3355 万元素 bit-identical**，prefill +0.66%、decode +0.60%。

**根因是上游文档写错了**：`simd.py:957` 把 `vcadd` 写成 "pairwise add reduction"，而真正的对折是相隔 12 行的 `vcpadd`。上一个会话照着 docstring 写的，**所以这不是粗心，是跟着错文档走**——和 Era A「跟着官方示例走」是同一种失败模式。

## 6. 如果只留一句话

**ForgeKernel 这条轨迹真正演示的，不是「工具很会调参」，而是「调参的天花板来自提问的层次」。** 39 条里有效的只有 6 条；把 prefill 抬过 1.0 的两下都在 kernel 外面；而两次最大的方向修正，一次来自操作者指出范式错了，一次来自参考资料让人换了个层次提问。**工具负责把每次尝试判准（这一点它做得很好——R53/R58/R74/R83 全是它在纠正人的判断），但换层次这件事，工具自己不会做。**
