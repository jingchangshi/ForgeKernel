# D3 评估：当前手段能否在 prefill 上达到厂商持平

> 本文只汇总**已归档的门控证据**，不引入任何未经门控的推断。所有"候选时长"均来自 AgentGates 同窗口配对（15 配对、15/15 quiet、bootstrap 95%）。

## 1. 结论先行

- **decode 64×4096：已达 EXCEED**（v16 候选：点估计 **1.3160×**，区间 **[1.3013, 1.3324]**，候选 0.002811 ms vs 厂商 0.003693 ms；15/15 quiet，精度与真实性 pass）。
- **prefill 8192×4096：未达标**。候选时长已从 0.0801 ms 降到 **0.0745 ms**（约 -7%），但厂商同一指标在 **0.0523–0.0645 ms** 之间波动，因此比值在 **0.68–0.83** 之间，仍差 **约 30%**（按厂商最好读数计）。

## 2. 候选时长的演进（唯一稳定的比较量）

| 版本 | 关键改动 | 候选时长 | 该窗口比值 |
|---|---|---|---|
| v4 | 单阶段 + 交错分区 | 0.0801 ms | 0.757 |
| v5 | 单阶段 + 每核连续分区 | 0.0794 ms | 0.830 |
| **v15** | **两阶段 + 每行寄存器（无共享态）** | **0.0755 ms** | 0.830 |
| **v16** | **v15 + x 四缓冲** | **0.0745 ms** | 0.715（decode 认证 1.3160×） |
| v7 / v8 / v9 / v17 | 其它调度组合 | 0.081–0.086 ms | 0.61–0.74 |

> 比值列不可横比：各窗口的厂商读数差异达 ±18%，比值的波动主要来自厂商侧，不来自候选。

## 3. 差距的构成（msprof 归因）

| 项 | v15 | 厂商 | 差 |
|---|---|---|---|
| vec 忙碌 | 41.0 µs | 37.2 µs | +10% |
| mte2（读） | 76.2 µs | 69.9 µs | +9% |
| mte3（写） | 77.4 µs | 63.8 µs | **+21%** |
| 总时长 | 88.1 µs | 75.3 µs | +17% |

**算力侧已基本追平**（曾比厂商多 63%，两阶段改造后只多 10%）。剩余差距集中在 **DMA 吞吐**：我们双向约 0.84 TB/s，厂商 0.91–1.0 TB/s。

## 4. 已排除的手段（附证据）

| 手段 | 结果 |
|---|---|
| 调度参数（rows 2/4/8、stages 2/3/4、y 1/2/3） | 除明显更差的组合外，均在噪声内（`evidence/r58-variant-table.json`、`r62-dma-bound.json`） |
| 每核连续分区 | 候选时长无变化（0.0801→0.0794，噪声）；此前报的 +8.9% 已撤回（`r58-correction-partition-claim.json`） |
| 两阶段 + 共享缓冲 | **有真实竞争**：rows=2 全尺寸错误，batch=128 不确定（`r59-two-phase-race.json`） |
| 两阶段 + 每行寄存器 | 有效，候选 -5%（v15），且全部尺寸正确且确定性 |
| `annotate_unlimit_memory` | 不放宽 launch 阶段 UB 检查（286720 B 必拒）（`r52-ub-*`） |
| `vsqz`/`vusqz` | 不是平方和原语，无法减少指令（`r56-v5-precision-coverage.json`） |
| bf16 `vmula` | 无混合精度 FMA |
| `T.gemm` 求 `X·Xᵀ` 对角线 | 设备编译失败，原因未隔离，不能推广为工具链结论 |

## 5. 若要达标还差什么

按每 64 元素约 10 条向量指令（无可用融合原语）与实测 DMA 吞吐，候选需再减少 **约 25–30%**。可预期的两条路：

1. **DMA 吞吐提升**：需要比 32 KB/次更大的连续传输或不同的拷贝引擎用法；当前 TileLang 接口未暴露相关旋钮。
2. **向量指令数下降**：需要硬件级融合（bf16 FMA、cube 通路），当前均不可用或未验证。

在两者都不可得的前提下，**本机、本工具链上 prefill 持平不可达**；这一判断以第 3、4 节的量化证据为限，不外推为硬件能力上限。

## 6. 未达标状态下的建议

- 保留 **decode 达标**的认证结果与 v16 候选。
- prefill 以 `FAIL` 如实记录，并保留可复现脚本与 15/15 quiet 原始报告。
- 若后续获得 DMA 相关接口或融合原语，从 v16（0.0745 ms）继续。

| 形状 | 判定 | 点估计 | 95% 区间 | 候选 | 厂商 | quiet |
|---|---|---|---|---|---|---|
| decode 64×4096 | **EXCEED** | **1.3160×** | [1.3013, 1.3324] | 0.002811 ms | 0.003693 ms | 15/15 |

## 8. 拷贝路径下限（R64 实测）

纯数据搬运微基准（64 MB 进 + 64 MB 出，经 UB，无计算）：

| 结构 | 聚合吞吐 | 用时 |
|---|---|---|
| 32 KB 块、双缓冲 | 1.72 TB/s | 0.0781 ms |
| 64 KB 块、3 级流水 | **1.73 TB/s** | **0.0778 ms** |
| 128 KB 块、2 级流水 | 1.71 TB/s | 0.0786 ms |

- **写路径饱和在约 1.13 TB/s**，且完全不随块大小变化；读可到 2.13 TB/s。
- 更大的块（128 KB 配 3 级、256 KB）因 `dyn_ubuf` 超限在 launch 阶段被拒。

对照：**我们的完整内核 0.0745 ms，已经持平甚至略优于"纯拷贝同样字节"的 0.0778 ms**；而厂商用 **0.0527–0.0645 ms** 完成整个算子（聚合 2.0–2.4 TB/s）。

**因此 residue 不在算术调度，而在数据搬运路径**：厂商能以超过 TileLang 拷贝路径的方式搬同样的字节。此结论限于"本机 + 本工具链拷贝路径的实测值"，不外推为硬件上限。

## 9. 聚合吞吐天花板（R65 实测）

- 写路径：**1.11–1.13 TB/s**，对元素宽度（bf16/float32）、块大小、缓冲深度、对齐偏移**均不敏感**。
- 读路径单独可达 2.13 TB/s，写单独 1.13 TB/s，但**两者并发时合计只有约 1.65 TB/s**（128 MB 用 0.0778 ms），说明两个方向争用同一搬运资源。
- 我们的完整内核 **0.0745 ms** 已经低于该纯拷贝用时；厂商 **0.0527 ms** 对应聚合 **2.43 TB/s**，比该天花板高约 **47%**。

由于字节数是固定的（bf16 双向各 64 MB），在本拷贝路径内**无法**通过算术调度、缓冲调优或分区来弥补这 47%。
