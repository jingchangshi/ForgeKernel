## 1. 测量口径（先说清楚数字怎么来的）

所有性能数字都基于**同窗口配对**测量，不是两次独立运行相除：

- **计时 basis**：`tilelang.profiler.msprof.bench_with_msprof`，读 `torch_npu.profiler` 的 FFTS 逐核时长（`dur_ns/1e6` ms），**排除 cache-flush 核**。这是 host-free 的设备时间，不受 Python 调度抖动影响。
- **配对方式**：同一窗口内 A/B 与 B/A 交替，相同输入输出分配、warmup 顺序；判定用配对差值的 bootstrap 95% 区间，**逐 shape**，禁止几何平均。
- **阈值（事先声明）**：MATCH = 点估计 ≥ 1.0 且 95% 下界 ≥ 0.98；EXCEED = 下界 > 1.0；FAIL = 区间上界 < 1.0；其余 RETEST。
- **争用处理**（本次实测后收紧，见 §5）：contended / sparse 窗口**一律剔除**出判定样本。

**为什么必须配对**：这台机器绝对设备时间跨 run 会漂移 2.5 倍。同一份代码 `vendor_ms` 在干净卡上为 0.0514 ms，在邻居占用时读到 0.0786 ms。只有**同一窗口内的比值**才有意义。

## 2. 起点：仓库示例内核的真实水平

第一次在昇腾上编译并测量 TileLang 的 RMSNorm 示例内核（脚本 `probe_bf16_rmsnorm.py`，每 shape 独立冷 cache）：

| 形态 | TileLang | 厂商 | 比值 | 精度 max_abs |
|---|---|---|---|---|
| 8192×4096 bf16（预填充） | 0.1634 ms | 0.0514 ms | **0.3148×** | 0.03125 |
| 64×4096 bf16（解码） | 0.004683 ms | 0.004019 ms | **0.8583×** | 0.00390625 |

**这就是起点**：预填充慢 3.18 倍，解码慢 1.17 倍。厂商侧自身的 max_rel_err 为 0.00775，与候选同量级——说明**双方都贴在 bf16 舍入地板上**，精度不是差距来源，性能才是。

> 口径提醒：这张表来自单进程冷测量（`do_bench`）。同一内核后来在配对窗口里测到 0.3224（预填充）与 0.9939（解码），差异见 §4.2。

## 3. 诊断：瓶颈到底在哪（这一层的证据质量最高）

### 3.1 不是算力不足，是数据搬运没喂饱向量单元

用 msprof 采集两个实现的 AIV 管道占比（4096×4096 bf16，同一时刻同一卡片）：

| 管道 | 示例内核 | 厂商算子 | 读法 |
|---|---|---|---|
| `aiv_vec`（向量） | 84.9% | 80.7% | **两边都已是向量受限**，候选甚至更满 |
| `aiv_mte2`（搬入） | **32.0%** | **64.2%** | 候选搬入只有厂商一半 |
| `aiv_mte3`（搬出） | **12.6%** | **44.9%** | 候选搬出只有厂商的 28% |

**结论：差距不在算术，在 DMA 流水效率。** 候选的向量单元已经 85% 忙，但数据供给只有 32%，所以它在**空转等数据**。

另有一个对候选有利的事实：厂商算子返回 `(y, rstd)` **两个张量**，任务只需要 `y`。所以厂商臂做了**严格更多的工作**，这个比较没有偏袒候选。

### 3.2 行分块是真杠杆，但已接近结构上限

扫描"每核每次处理几行"（`rows`，8192×4096 bf16）：

| 每核行数 | 设备时间 | mte2 | 相对 rows=1 |
|---|---|---|---|
| rows=1 | 289 µs | 34.2% | 1.00× |
| rows=2 | 189.6 µs | 58.9% | 1.52× |
| rows=4 | **164.2 µs** | 53.4% | **1.76×** |
| rows=8 | ❌ UB 溢出 | — | 271360 B > 256 KiB 上限（实测） |

**这是本次唯一被量化验证的优化杠杆**：1→4 行带来 **1.76×**（289→164 µs），证实了"MTE2 饥饿"的判断。但 **rows=8 放不进 UB**，所以单靠加大行批无法继续接近厂商。

### 3.3 带宽算术给出剩余差距的归属

```
8192×4096 bf16: 读 X 64 MiB + 写 Y 64 MiB = 128 MiB 总流量（W 仅 8 KiB）
厂商 51.4 µs  →  128 MiB / 51.4 µs  = 约 2.6 TB/s 有效带宽
候选 163.4 µs →  128 MiB / 163.4 µs = 约 0.8 TB/s 有效带宽
```

> 口径必须写明：以上按**读+写双向流量**计。若只算读侧（64 MiB），则厂商 1.30 TB/s、候选 0.41 TB/s——比值不变，但绝对值差一倍。本报告统一用双向口径，因为它对应内核实际必须搬动的字节数。

候选已达向量管道 85%，带宽却只有厂商的 1/3。**剩余 3.1 倍差距几乎全部在 DMA/流水效率**，不在算术。这直接指向下一步优化目标：**UB 上限（实测 256 KiB）内的 copy pipelining**，而不是继续调算术。

### 4.2 已完成：测量方法学（决定了后续所有数字可信）

这一步不是"优化性能"，但它是一切性能结论的前提，且产出了**四个必须记录的发现**：

**（a）配对能吸收轻量/突发邻居，不能吸收持续饱和争用**（两者都实测过，先前的结论已更正）：

| 争用强度 | 配对比值变化 | 出处 |
|---|---|---|
| 突发邻居（最差单对 0.878，中位 0.3124） | 中位仅移动 **0.8%** | `paired_shared_card_validation` |
| 持续 AICore 99%（8192×4096） | 0.3224 → 0.6615（**+105%**） | `contention_bias_measured` |
| 持续 AICore 99%（64×4096） | 0.9939 → 0.8273（**−17%**） | 同上 |

**偏差方向随 shape 反转**，所以争用不是保守误差：**2.052× 的膨胀足以让真实 0.478 的实现被报成 0.98，越过 MATCH 门槛**。因此验收判据改为 **contended 窗口一律剔除**，quiet 不足 9 个或占比 <70% 判 RETEST。

> 更正说明：早先证据里"在 99% 忙的卡上配对仍成立（0.3124 vs 0.3148）"这一条，其"99% 利用率 / 21309 MB"两个条件数字是**手工写入的**，产生比值的脚本 `paired_bench.py` 完全不采样 `npu-smi`。该条已标注 provenance 缺陷，结论收窄为"配对中位数抗突发扰动"。

**（b）canary kernel 作为争用检测器不灵敏**：全程 AICore 99% 时，canary 膨胀 ≥1.15 仅 **3/9（33%）**。因它只跑约 0.06 ms，噪声与信号同量级。已降级为**辅助阳性信号，绝不可用作否证**；主判据是进程外 AICore 轨迹（本次 9/9 全部正确标出）+ 设备进程表。

**（c）`npu-smi` 采样受物理限制**：单次调用实测 0.79–1.04 s（全表 0.80–2.39 s），**100–200 ms 高频轨迹在本机不可得**。要求该密度只会迫使实现伪造 witness。改用 canary（分辨率等于测量分辨率）+ 保留 `npu-smi` 作为失效模式不同的第二证据。

**（d）精度判据的判别力用 ulp 论证**：`2^-7` 是 bf16 的**一个 ulp**，比较必须用 `<=`（用 `<` 会误杀厂商本身）。正确实现在 8192×4096/normal 上读到恰好 1.000 ulp——零余量是 bf16 算术的必然，不是判据漏洞。故意用 bf16 累加的实现在全 6 组合读出 **2.053–5.525 ulp**，最窄拒绝余量 **2.05×**。floor 对诚实实现留有约 220 倍空间。

### 4.3 未落地：真正把内核做到达标（这是剩余工作）

**必须明确：目前没有任何一轮"生成候选 → 测量 → KEEP/REVERT"的自动优化迭代被真正跑完。** 已定位的杠杆与已存在的能力如下：

| 行分块 rows 1→4 | ✅ 已量化验证 1.76× | 但**示意内核本就采用 rows=4 自适应**，所以这 1.76× 是"诊断出的杠杆"，不是"本轮优化赚到的" |
| rows=8 | ❌ 结构上限 | UB 需要 271360 B，超过实测 256 KiB 上限 |
| copy pipelining / UB 预算优化 | 🔍 已定位，未实现 | §3 全部证据指向这里，是剩余 3.1× 的主战场 |

## 5. 最终性能判定（基于剔除争用窗口后的干净样本）

数据源 `artifacts/accept-genuine.json`（12:53，10/10 窗口均 quiet，无争用剔除）：

| 形态 | 点估计 | 95% 区间 | 判定 | 读法 |
|---|---|---|---|---|
| 8192×4096 | **0.3224** | [0.3115, **0.3268**] | **FAIL** | 区间上界仍远低于 0.98，噪声无法挽救 → 确定慢约 3.1× |
| 64×4096 | **0.9939** | [0.9711, **1.0260**] | **RETEST** | 区间跨 1.0 → 与厂商**未分离**，不能声称达标也不能声称落后 |

**测量质量旁证**（说明上述结论不是噪声）：两臂离散度极小——8192×4096 候选 max/min 仅 1.01×、厂商 1.07×；`ratioSpreadP90P10` 为 1.06 / 1.09，远低于 1.25 上限。所以 FAIL 是**真实且稳定**的结论。

**三次独立测量互相印证预填充水平**：0.3148（probe）、0.3124（paired_bench 15×20）、0.3224（accept 10 窗口）。**这是同一 artifact 在同一机器上可复现的证据**，不是单次运气。

## 6. 优化方向（按证据强度排序）

1. **copy pipelining / MTE2 供给**（最强证据）：候选 mte2 仅 32%、mte3 仅 12.6%，而 vec 已 85%。提高数据供给流水是剩余 3.1× 的主要来源。目标是把 mte2 推到厂商的 64% 量级。
2. **UB 预算内的分块策略**：rows=8 溢出的根源是 `rows*d*2 + rows*d*4*2` 的超额（第 36 行同时驻留 bf16 与 fp32 副本）。若能改为就地转换或复用缓冲，rows=8 可能可容纳。
3. **解码形态单独优化**：64×4096 只有 3.7 µs，启动/同步开销占比大。厂商 3.71 µs 已达此量级的下限，候选 3.74 µs 实际已几乎持平，重点应放在**降低固定开销**而非吞吐。
4. **建立 `hw_kb/tilelang-ascend/`**：把 §3 的管道归因、row tile 上限、UB 溢出阈值写进知识库，避免迭代重新发现。
