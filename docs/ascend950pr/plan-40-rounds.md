# RMSNorm 40 轮优化计划（Ascend950PR / TileLang-Ascend）

状态：执行中。更新：2026-11-02。上承 `workplan.md`、`simdvf-dma-plan.md`、`simdvf-dma-review.md`。

## 0. 目标（可判定的定义）

逐 shape 达到：**点估计 speedup ≥ 1.0 且配对 bootstrap 95% 下界 ≥ 0.98**，其中 speedup = 厂商设备时长 / 候选设备时长，同一测量窗口内配对。

- prefill 8192×4096 bf16，decode 64×4096 bf16，eps=1e-6，fp32 统计，末尾一次 bf16 舍入。
- 两 shape 分别判定；禁止用几何平均掩盖任一 shape 失败。
- 证据不足（窗口不够、见证不可用）判 **RETEST**，不得判 PASS。

**当前起点（诚实）**：prefill ≈0.39x（SimtVF cw4，读数受争用影响）；decode 约 1.09x 但**多次独立验收均为 RETEST**，未认证。新路线 SimdVF+DMA 的 bf16 载入已实测正确，归约/写回/性能未验证。

## 1. 阶段与轮次

| 阶段 | 轮次 | 目标 | 出口门 |
|---|---|---|---|
| A 归约打通 | 1–6 | SimdVF 内跨 lane 归约到标量、bf16 写回、rstd 广播；单行 4096 正确 | 单行输出对 CPU float64 相对误差 ≤ 2^-7 |
| B 完整内核 | 7–12 | 多核(64)行映射 + DMA 流水；两 shape 正确 | 两 shape 全输入族精度通过 |
| C 计时与优化 | 13–18 | 同窗口配对计时；融合两遍、减指令 | 有可信配对数据，且优于 SimtVF 基线 |
| D 攻克差距 | 19–26 | 在线单遍、split-D、更大向量、UB 调优 | prefill ≥1.0 或明确记录不可达原因 |
| E 加固 | 27–32 | 保留集种子、极端输入、边界行 | 精度与鲁棒性全绿 |
| F 独立验收+闭环 | 33–38 | AgentGates 独立验收 + ForgeKernel KEEP/REVERT | 15+ 配对、多进程、见证充分 |
| G 终验归档 | 39–40 | 逐 shape 终验、证据归档 | 两 shape 均达标并归档 |

## 2. 每轮固定动作

1. 读当前证据与最近阻塞点；只攻击**最高未知**。
2. 用探针/最小内核验证，标注 [已实测]/[未验证]。
3. 通过门才前进；失败即回退并记录原因。
4. 每轮结束提交：代码/证据 + 一行结论。
5. 每 5 轮做一次诚实复评：是否偏离目标、是否该换路线。

## 3. 关键决策门

- **D1（第 6 轮）**：若 SimdVF 归约/写回无法在 6 轮内做到单行正确 → 回退 SimtVF 路线，转攻 DMA/融合/布局，不再纠缠微指令。
- **D2（第 12 轮）**：若完整内核正确但慢于 SimtVF cw4 → 放弃 SimdVF，保留 SimtVF 并转 D 阶段其它手段。
- **D3（第 26 轮）**：若 prefill 仍 <1.0 → 明确写出"当前手段不可达"的具体证据，转入 E/F 把已有最优如实验收，不虚报。
- **D4（第 38 轮）**：验收不足 → RETEST，延长而不放宽判据。

## 4. 风险与对策

1. **归约开销吃掉收益**：先在 A 阶段量归约指令占比；必要时用部分和 + 二次小归约。
2. **bf16 写回语义错**：一律先对 CPU float64 验，错即停。
3. **共享卡争用**：只做同窗口配对，不用跨 run 绝对时间；见证不足判 RETEST。
4. **UB 预算**：每个新内核按自身分配实测，不套用 262144 B 的单探针观测。
5. **agent 闭环不稳定**：两名成员已连续失败；闭环只作为 F 阶段的一个证据源，不作为唯一路径。

## 5. 现有后台 run 的处理

两个 ForgeKernel run（PyTorch 参考 run 与厂商参考 run）仍在 teacher 阶段。**第 1 轮内**检查其预算并收割或停止；若产出候选，作为 F 阶段 KEEP/REVERT 的输入，但不作为达标证据。

## 6. 停止条件

- 达成：两 shape 均 ≥1.0 且下界 ≥0.98，独立验收通过并归档。
- 不可达：D3 触发且证据充分 → 如实报告逐 shape 现状与差距，不标完成。
- 预算耗尽（40 轮）：如实汇总，未达标则不标完成。

## 7. 轮次细则

- R1：钉死 vcadd 归约链；测归约开销。
- R2：钉死 bf16 `vsts` 写回与 rstd 标量广播。
- R3：单行 4096 平方和 → 标量，对 float64 验。
- R4：单行完整 RMSNorm 原型，对 float64 验。
- R5：多行单核正确性；UB 实测。
- R6：决策 D1。
- R7–R12：多核映射、DMA 流水、两 shape 正确性，D2。
- R13–R18：配对计时框架、融合、指令精简。
- R19–R26：结构性手段（在线单遍/split-D/布局），D3。
- R27–R32：输入族与保留集加固。
- R33–R38：独立验收与闭环，D4。
- R39–R40：终验与归档。

## 8. 进度日志

### R1–R2（API 打通）
bf16 载入、bf16 写回、标量广播、rstd 链全部实测通过。证据：`evidence/simdvf-r1-reduce-2026-11-02.json`、`evidence/simdvf-r2-api-2026-11-02.json`。

### R3–R5（内核打通）
单行对 float64 完全一致；多核 8192×4096 正确；同窗口配对 0.539x，w 预转换后 0.581x。归档 `candidates/rmsnorm_simdvf_v1/kernel.py`。

### R6（归因与决策 D1）
- 单次 profiler 报告内核 vec 73% / mte2 65% / mte3 23%，厂商 vec 52% / mte2 92% / mte3 78%；各管道可能重叠，不能由此证明瓶颈或理论性能上限。
- 一种 `UNPK_B16` + `part=1` 组合产生零，不足以排除其他加载布局；混合精度 `vmula` 也仅有一次失败探针。
- rows/stages 扫描为顺序、非配对探索数据；0.622x 不可作认证或跨运行改进结论。
- 继续验证 SimdVF 路线；归档 v1/v2 曾使用无效 dtype `bf16`，不能把实验脚本的结果视为归档候选的验收结果。

### 下一阶段修订策略（Phase D 提前）
`T.gemm` 是一个待验证假设，可计算 `X · Xᵀ` 的对角线，但会计算大量无用非对角元素；此前两个探针的设备编译失败，原因尚未隔离，不能推广为工具链不支持或断定它是唯一方案。优先完成候选正确性、生成代码审查与同窗口对照，再决定是否继续此方向。
### R46–R58（门控化与更正）

- **验收协议成为唯一判据**：所有性能结论均来自 AgentGates 的同窗口配对门（15 配对、15/15 quiet、bootstrap 95%）。单进程筛查多次给出与实际不符的"改进"（曾预测 +12%，门控为 0），今后筛查只用于排序假设。
- **decode 64×4096 认证 EXCEED**：点估计 **1.2809×**，区间 **[1.2470, 1.3087]**，候选 0.002777 ms vs 厂商 0.003596 ms（证据 `evidence/accept-v4-decode-r51-raw.json`）。v5 的 decode 路径与之代数等价（rows=1、iters=1 时两种分区公式都退化为 `core*d`）。
- **prefill 8192×4096 未达标**：候选时长在多次门控中稳定在 **0.079–0.083 ms**，厂商在 **0.055–0.065 ms**（±18%），比值约 **0.70–0.75**。
- **两次更正**：
  1. 早期 prefill 的 0.53–0.62× 是我们自己的 ForgeKernel run 占用同一张卡造成的低估，已作废；
  2. R54 曾报"连续分区把 0.757 提到 0.825（+8.9%）"，**已撤回**——候选时长只从 0.0801 变到 0.0794 ms（约 0.8%，噪声），差异来自厂商窗口波动（0.0591 → 0.0645）。
- **已验证的否定结论**：`annotate_unlimit_memory` 不改变 launch 阶段的 UB 检查（286720 B 必拒）；`vsqz`/`vusqz` 不是平方和原语；bf16 `vmula` 无混合精度；`T.gemm` 设备编译失败原因仍未隔离。
- **验收门修复**（AgentGates `53b388a`）：候选未产出测量且未观测到任何 kernel 时，真实性记 `inconclusive` → RETEST，而不是误判为委托厂商。门控测试 78 项通过。
- **精度**：v5 在 prefill 的门控 3 个输入族（normal/near_zero/tiny）与 decode 的 4 个输入族上全部通过，误差远低于 2⁻⁷。
- **环境**：共享卡上常有 2–4 名外部用户（root 的 pytest 等），大量尝试被判 RETEST；这是环境而非候选问题。
- **结论**：decode 达标；prefill 仍需 **20–30%** 的时间削减。给定每 64 元素已约 10 条向量指令（无可用融合原语），且 vec 忙碌约 60 µs、DMA-in 约 65–69 µs，单纯调度/分区无法弥补，需硬件级融合或更强的重叠手段。
### R59（两阶段调度被否定）

- 两阶段内核（先全部归约、再全部缩放，用共享缓冲传每行 rstd）**有一个真实竞争**：rows=2 形式在所有测试尺寸上都错，且 batch=128 时**不确定**（同一输入 5 次结果不同，rel=1.0）。给该缓冲显式声明流水版本（v14）**也没修好**（rel 23.4 与 NaN）。
- rows=4 形式恰好 10 次重复完全一致且对 float64 正确，但那是**运气**，不能作为普遍安全证明。
- 因此 v10/v11/v13/v14/v14b 全部标记 REJECTED；其 0.0733 ms 也**不得**作为性能结论。
- 接受的 prefill 候选仍是单阶段逐行内核 **v5（约 0.079 ms）**。
- 附带事实：TileLang 前端会把 `T.prim_func` 里的 Python `for r in range(...)` 转成设备循环，所以"Python 层展开行"这种写法在核函数体内不成立（v13 因此报 `list indices ... not Var`）。

### R60–R71（收尾阶段）

- **R60**：v15 用「源码级显式展开 4 行 + 每行寄存器」实现两阶段，全部尺寸正确且确定性；无共享状态，规避了 R59 的竞争。
- **R61**：v15 门控 prefill 候选 **0.0755 ms**（此前 0.0794），首次确认两阶段有效。
- **R62**：归因显示算力侧已基本追平（vec 41.0 µs vs 厂商 37.2 µs），瓶颈转到 DMA；加深缓冲无效。
- **R63**：v16 成为单一候选，decode 认证 **1.3160×**；落成 D3 评估文档。
- **R64**：拷贝路径微基准：未设策略时读写合计约 1.7 TB/s，纯拷贝 128 MB 需 0.078 ms。
- **R65（关键）**：**发现 L2 缓存策略是决定性旋钮**——写路径显式 `NORMAL_FV` 后从 1.13 提升到 **3.08 TB/s（2.7×）**；v18 候选降至 **0.0648 ms**。R64 的"已触底"结论**撤回**。
- **R66**：微基准排名不能搬到内核（读路径 `NORMAL_LV` 反而更慢）；v21 全路径 `NORMAL_FV`，decode **1.3559×**。
- **R67**：v23（stages=4 + 全 `NORMAL_FV`）成为最优：decode **1.3726×**，prefill 候选 **0.0651 ms**。
- **R68–R70**：系统性否定——rows=2、rows=8、stages=5/6、8 条累加链、y 三缓冲、读写异构策略、手动 `order`/`stage` 流水调度**均不优于 v23**。
- **R69**：两形状在**独立窗口复现**——decode **1.4056× [1.3783, 1.4493]**，prefill **0.8133 [0.7956, 0.8432]**。
- **R71**：Phase G 归档，生成 `archive-manifest.json`（含各文件 sha256）。

**阶段结论**：decode 达标且可复现；prefill 未达标（候选 0.065–0.069 ms vs 厂商 0.050–0.062 ms）。所有优化手段已系统测过，v23 为最优。

### R72–R78（终验与收尾）

- **R72**：归档包在全新空缓存下复现成功（decode 1.3550×）；并排除"加大 DMA 块"这一想法——设了 L2 策略后 32 KB 即达 1.757 TB/s，64 KB 反而 1.725 TB/s。
- **R73**：把差距定位到**混合读写流量效率**：只读 2.35 / 只写 3.08 TB/s，混合后我们 1.97、厂商 2.42 TB/s。
- **R74**：更正——prefill 的**绝对时长在窗口间漂移 ±20%**，比值才是稳定量（0.771–0.813）。
- **R76**：文档数字与原始证据逐项审计，5 项全部精确一致；归档清单哈希重新生成并与磁盘一致。
- **R77**：第四个干净窗口，prefill 比值 **0.8502 [0.8294, 0.8830]**，仍是四窗口中最好且仍不达标。
- **R78**：定稿最终汇报与交付清单。

**终局**：decode 达标（1.355–1.406，三窗口）；prefill 四窗口 0.771–0.850，均不达标，慢 15–23%。所有已识别优化杠杆均已系统测试并归档。
